# Nido voice and visual identity

Nido is a practical VM manager with an affectionate 1980s computing aesthetic.
The reader should understand what the software does before decoding a metaphor.

## Voice

- Lead with the actual capability, command or error. Add personality sparingly.
- Use the nest / hatch metaphor for VM creation and the arcade metaphor for
  optional headings or release messages, without replacing technical names.
- Keep product instructions direct. An image is an image, a template is a disk
  template, and `stop` terminates the managed process. Do not rename these
  behaviors into something the implementation does not do.
- Do not promise instant boot, constant disk usage, root login or complete
  security isolation. State conditions and measured qualification accurately.
- Use `-` for prose separators. Prefer readable headings over emoji on every
  line. Keep command examples copyable and JSON faithful to the contract.

Good introductory copy: **Real VMs. Agent-ready.**

Good supporting copy: **Hatch your agents. Let them fly.**

## Visuals

Use the retro workstation, luminous circuit egg and nest. Dark navy, cyan,
coral and restrained violet provide the current editorial palette. Keep a clear
silhouette and generous spacing; avoid tiny labels and walls of neon effects.
See [visual assets](../resources/README.md) for delivered files and consumers.

Use real screenshots only when they show the current product and reveal no
private data. Use diagrams for system concepts, with text alternatives.

## Commits and pull requests

Use a conventional prefix, a concrete outcome and a small touch of personality:

```text
docs(readme): refresh the nest's field guide 🪺
fix(mcp): preserve saved VM arguments on omitted updates 🛠️
```

PR descriptions explain the problem, resulting behavior and validation. A themed
title must not obscure what changed or overstate the evidence.
